1. 측정 근거와 한계

영역현재 확인한 상태개발에 미치는 영향
코드 점검카탈로그 806개 로딩, registry 오류 0. 재개 신호 27개, 로컬 시간 예산 신호 721개. 정적 코드 검사 결과.코드 존재와 실제 운영 성공을 구분해야 함. 신호가 없는 85개도 외부 프로세스 제한은 별도 적용 가능.

수집 결과조용히 반환하는 실패와 신규 0건을 구분하기 어려움. 사이트별 네트워크·예외 처리 구현이 제각각.명시적 실패 계약을 도입하고 우선 수집기부터 확대. 0건만으로 실패 판정하지 않음.
파일 처리공통 다운로드 함수의 형식 검사·PostgreSQL 지원 보강 필요. 메타데이터→PDF→텍스트 자동 큐 연결 미완료.파일 처리 작업/재시도/상태 모델이 별도로 필요. DB 플래그만으로 파일 존재를 보장할 수 없음.
운영 환경이전 읽기 전용 점검에서 구버전 스키마와 빈 파일 볼륨 확인. 운영 환경은 이번 작업에서 변경하지 않음.배포 시 마이그레이션, 실제 파일 경로 연결, 기존 데이터 대조를 통과해야 인수 가능.
FE / 접근건강 점검 화면 구현됨. 백필 시작 UI, 이력 탐색, 사이트명 중심 예약 편의 보강 필요. 사용자 접근 인증은 배포 경계에 의존.공개 운영 전 인증 경계 확정. 내부 단일 운영자와 외부 다중 사용자 범위를 구분.

근거: delivery/health/inventory.py 및 전수 inventory, crawler/pdf_downloader.py, delivery/worker/worker.py, DOAJ 수집기, BE /progress, FE 백필·작업 상태 표시. 외부 서비스 응답과 데이터 전송 상태는 별도 시점의 사실이며 최신 운영 보증이 아닙니다.

3. 실행 순서와 재산정 시점

  1. 1차 수정과 회귀 검증을 끝내고 개발 기준선을 고정합니다.
  2. 전체 health 검사로 접근 차단·설정 누락·파싱 문제·별도 점검 필요 항목을 분류합니다. 기본값(2개 동시, 사이트당 60초)에서 시간 제한 합계만 약 6.7시간이며 시작 비용·리소스 제한이 추가될 수 있습니다.
  3. 실수집 우선 사이트를 정해 2·3단계를 진행합니다. 인증정보 없는 사이트는 설정 대기로 관리하며 정상 판정을 내리지 않습니다.
  4. 4단계 UI는 1차 상태 모델에 맞춰 진행합니다. 외부 공개가 필요하면 5단계를 앞당깁니다.
  5. 6단계에서 전달할 정확한 코드 버전으로 설치·업데이트를 검증합니다. 계획상의 완료와 실제 고객 배포 완료는 따로 기록합니다.

재산정 조건: 사이트별 장애 수, 다운로드 대상 파일 크기·형식, OCR 필요 여부, 운영 인증 방식, 고객 OS/볼륨 경로. 이미지 스캔 PDF의 OCR·모델 비용, 전문 검색/RAG, 다중 사용자 권한, 대용량 병렬화는 이 기준 범위에 포함하지 않았습니다.

2026-10-08 추가 구현

2단계의 기본 파일 큐·전용 워커·FE 선택/상태/재시도 기능을 구현했습니다. 사이트별 실행에서 문서 정보 → PDF → 텍스트를 연결하고, 기존 파일 재사용·시간 제한·제한된 재시도·중지를 지원합니다. 일괄/예약의 파일 옵션과 과거 자료 전수 복구는 이번 범위에 포함하지 않습니다.

실제 PDF 파서와 파일 처리 분기는 로컬 테스트로 검증했습니다. 현재 세션의 Docker·로컬 소켓 접근 제한으로 PostgreSQL 통합 테스트 및 브라우저 실행 검증은 대기 상태입니다. 따라서 2단계 전체 인수 완료로 표시하지 않습니다. 기존 2026-10-07 검증 수치는 그 시점의 코드에 대한 결과입니다.

4. 이번 구현의 경계와 검증

명시적 실패 계약은 DOAJ부터 적용했습니다. 다른 사이트의 조용한 실패는 여전히 신규 0건으로 끝날 수 있어 문구와 health 결과를 함께 봐야 합니다. PDF 검증은 공통 다운로드 함수의 헤더 확인이며, PDF 전체 구조/기존 파일 전수 검사 또는 각 수집기의 독자 저장 경로 검사는 아닙니다.

DOAJ의 페이지 내 위치 커서는 동일한 목록 순서를 전제로 합니다. 원격 목록이 실행 사이에 바뀌는 경우의 완전성 보장은 별도 검증 대상입니다. 파일과 DB 변경을 하나의 트랜잭션으로 묶지 못하므로 파일 교체 직후 DB 장애가 발생하는 경우는 2단계 대조·복구 작업에서 다룹니다.

최종 검증: Python 326개 테스트, FE 297개 테스트 통과. FE 타입 검사·린트·프로덕션 빌드 통과. 일회용 PostgreSQL에서 API·작업 상태 전이·PDF 저장을 검증했습니다. 실제 브라우저의 합성 API 데이터로 백필 5개 상태를 확인했고 PC/모바일 페이지 오류 및 화면 전체 가로 넘침은 없었습니다. 외부 806개 재접속 검사는 이번 구현에서 수행하지 않았습니다.

운영 컨테이너, 고객 저장소, 기존 납품 압축파일은 이번 구현으로 자동 갱신되지 않습니다. 새 전달본은 6단계 인수 검증을 거쳐 생성합니다.
