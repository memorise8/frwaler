1.개요

본 문서는 Libertree — 웹페이지 데이터 수집·분석·요약 서비스의 실제 배포 인프라 아키텍처를 기술한다. 본 시스템은 클라우드가 아닌 온프레미스(on-premise) 단일 호스트 로컬 구성으로 운영되며, 모든 데이터·연산·저장이 하나의 서버 안에서 완결된다.

핵심 설계 원칙은 다음과 같다.

  • 단일 호스트 완결성 — 크롤러, 관리자 앱, 열람 앱, 데이터베이스, 블랍(원문 파일) 저장소, 요약 엔진이 모두 로컬 디스크와 로컬 포트로 연결된다. 외부 관리형 서비스(RDS·S3 등)에 의존하지 않는다.
  • SQLite 단일 파일 DB — 메타데이터는 libertree.db 단일 SQLite 파일에 저장하며 WAL 모드로 동시 읽기를 보장한다.
  • 파일 시스템 블랍 저장소 — 첨부 원문(PDF)과 추출 텍스트(TXT)는 프로젝트 루트의 libertree/ 디렉터리에 계층형으로 저장한다.
  • 읽기/쓰기 경로 분리 — 크롤러만 DB·블랍에 쓰기를 수행하고, 열람 앱은 데이터 마운트를 읽기 전용(read-only)으로만 연결한다.
  • 인증 게이트 — 웹 접근은 전부 HTTP Basic Auth(ADMIN_USER/ADMIN_PASSWORD)로 보호한다.

비용과 운영 단순성을 우선하여, 계약서상의 클라우드(AWS) 설계 대신 동일한 저장 규칙을 유지하는 로컬 구성으로 구현되었다. 상세 대비는 7. 요구사항 대비를 참조한다.

2.시스템 구성도

중앙의 SQLite(libertree.db)를 데이터 허브로, 쓰기 측(크롤러)과 읽기 측(관리자·열람 앱)이 분리된 구조다. 원문 파일은 별도 로컬 블랍 저장소에 보관하고, 요약은 로컬 요약 엔진이 담당한다.

관계 설명

  • 크롤러 → SQLite / blob : 크롤러는 유일한 쓰기 주체로, 수집한 메타데이터를 libertree.db에 upsert 하고 원문·추출 텍스트를 libertree/ 블랍 저장소에 기록한다.
  • 크롤러 ↔ Ollama : 텍스트 추출 후, 크롤러의 요약 단계가 로컬 요약 엔진(Ollama, 127.0.0.1:11436)을 호출하여 한국어 요약을 생성하고 그 결과를 DB의 요약 컬럼에 반영한다.
  • SQLite ← 관리자 앱(finolaw) : 관리자 앱은 libertree.db(및 레거시 papers.db)를 읽기 전용으로 열어 대시보드·검색·수집 관리 화면을 제공한다.
  • SQLite / blob ← 열람 앱(libertree-app) : 열람 앱은 데이터 디렉터리와 블랍 루트를 읽기 전용 바인드 마운트로 연결하여, 검토가 끝난 문서의 공개 검색·원문 열람을 제공한다. WAL/SHM 사이드카를 함께 마운트하여 실시간 갱신을 반영한다.

4.데이터 흐름

수집부터 열람까지 단일 파이프라인으로 이어진다. 각 단계는 크롤러 CLI 서브커맨드로 실행되며, 산출물은 중앙 DB와 블랍 저장소에 누적된다.

  1. 수집 — 크롤러가 대상 사이트를 순회하며 문서 메타데이터를 libertree.db에 저장한다.
  2. 첨부 다운로드 — 각 문서의 첨부 원문을 블랍 저장소에 .pdf로 저장하고 크기·해시를 기록한다.
  3. 텍스트 추출 — 원문에서 본문을 추출하여 같은 경로에 .txt로 나란히 저장한다.
  4. AI 요약 — 추출 텍스트를 로컬 요약 엔진에 넘겨 한국어 요약을 생성하고 DB에 반영한다.
  5. 검토/열람 — 관리자는 finolaw(3001)에서 검토하고, 최종 확정본은 열람 앱(3101)에서 공개 검색·열람된다.

5.배포 구조

배포는 Docker Compose 스택으로 구성된다. 수집·관리 스택(루트)과 공개 열람 스택(libertree-app)이 각각 독립 컨테이너로 구동되며, 포트 소유권이 분리된다.

포트 매핑 요약

  • 3001 — finolaw 관리자 앱(수집·관리 스택 내부 및 호스트 노출).
  • 3101 — libertree-app 공개 열람 앱(호스트 루프백 → 컨테이너 내부 3001로 매핑). 관리 스택의 3001 소유권을 침범하지 않는다.
  • 11436 — 로컬 Ollama 요약 엔진(크롤러 내부 호출용).

인증 (HTTP Basic Auth)

모든 웹 접근은 ADMIN_USER / ADMIN_PASSWORD 기반 HTTP Basic Auth로 보호된다.

  • finolaw : src/proxy.ts가 앱 전역 인증 게이트로 동작.
  • libertree-app : 앱 전역 인증 프록시가 라우트 매칭보다 먼저 동작하여, 자격 증명이 없으면 401을 반환. /api/health는 인증을 통과한 뒤 실제 카탈로그 조회까지 검증하는 readiness 프로브(정상 200 / 자격 오류 401 / 데이터 접근 불가 503).
환경 변수 LIBERTREE_HOST_APP_DATA_ROOT(데이터 디렉터리) · LIBERTREE_HOST_BLOB_ROOT(블랍 루트) · LIBERTREE_HOST_PORT(기본 3101)로 열람 스택을 구성한다. 시작 게이트는 쓰기 가능/누락 마운트, 변경된 데이터 경로, 크롤러·요약·외부 AI 키 환경 변수를 거부한다.

6.저장소 설계

SQLite (WAL)

메타데이터는 단일 파일 libertree-app/data/libertree.db에 저장한다. WAL(Write-Ahead Logging) 모드를 사용하여 크롤러의 쓰기와 열람 앱의 읽기가 동시에 진행되어도 잠금 충돌 없이 최신 상태를 조회할 수 있다. 라이브 -wal / -shm 사이드카 파일이 함께 존재하므로, 열람 컨테이너는 DB 파일 단독이 아니라 데이터 디렉터리 전체를 읽기 전용으로 마운트한다.

documents 테이블의 기본 키는 1조(1012)까지 안전한 INTEGER seq_id이며, 중복 방지 키는 (site_id, post_number, meta_url) UNIQUE이다.

블랍 계층 (12자리 4-4-4)

원문·추출 파일은 libertree/ 루트 아래에 12자리 zero-padded seq_id를 2단계 폴더(앞 4자리 / 다음 4자리)로 분산 저장한다. 각 leaf 디렉터리당 최대 10,000개 파일이 담기며, 전체 구조는 1조 건까지 수용한다.

경로 규칙:  {root}/{name[0:4]}/{name[4:8]}/{name}.{ext}
            name = f"{seq_id:012d}"

예시 (seq_id = 1):
  libertree/0000/0000/000000000001.pdf   ← 원문
  libertree/0000/0000/000000000001.txt   ← 추출 텍스트

예시 (seq_id = 123,456,789):
  libertree/0000/1234/000123456789.txt

PDF 저장 시 파일 크기와 SHA-256 해시를 산출하여 무결성 검증에 사용하며, 추출 텍스트는 동일 경로에 확장자만 다르게(.txt) 나란히 배치된다. 기본 루트는 환경 변수 LIBERTREE_BLOB_ROOT로 재정의할 수 있다.

이 블랍 레이아웃은 레거시 crawler/storage.py(루트 data/)와 완전히 분리되어, 기존 papers.db / data/ 구조에 영향을 주지 않고 독립적으로 동작한다.

7.요구사항 대비 (부록)

계약(REQ-2026-001)과의 차이

계약서상의 인프라 요구사항은 AWS 클라우드 기반이었다 — EC2 컴퓨팅, RDS PostgreSQL, S3 객체 스토리지, ECS 컨테이너 오케스트레이션. 그러나 현재 구현은 온프레미스 로컬 구성으로, 비용 절감과 운영 단순성을 우선하여 다음과 같이 치환되었다.

계약 (AWS)현재 구현 (온프레미스)
EC2 (컴퓨팅)단일 로컬 호스트 + Docker Compose
RDS PostgreSQL로컬 SQLite (libertree.db, WAL)
S3 (객체 스토리지)로컬 디스크 블랍 저장소 (libertree/)
ECS (오케스트레이션)Docker Compose 스택 (수집·관리 / 열람 분리)

저장 규칙은 동일하게 유지된다 — 12자리 seq_id의 4-4-4 계층 분산, SHA-256 무결성, 1조 건 수용 용량 설계는 그대로다. 유일한 차이는 저장소 루트가 클라우드 버킷/기존 data/에서 libertree/로 바뀐 점이다. 이로써 향후 클라우드(S3 등)로 이전하더라도 동일한 키 구조를 그대로 재사용할 수 있다.
