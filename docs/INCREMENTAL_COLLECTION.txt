공통 증분 수집 구현 및 검증 범위 (2026-10-12)

실행 경로
- delivery.worker.worker.run_job()에서 기존 incremental/full/backfill 작업을 사용한다.
- crawler.incremental.Collector가 목록 탐색 → 영속 대기 큐 → 오래된 항목부터 저장을 담당한다.
- 목록 끝이라는 명시적 증거와 대기 큐 저장 완료를 모두 충족해야 baseline_complete와 기준 ID/날짜를 저장한다.
- 기존 backfill cursor를 최초 완주 증거로 승격하지 않는다. crawl_site_progress에는 공통 상태의 세대/단계/저장 진도를, crawl_incremental_state에는 실제 소스 커서와 정렬 증거를 보관한다.
- native crawler.crawl() 직접 호출은 기존 경로다. 공통 기능은 delivery worker 경로로 실행해야 한다.

목록 및 저장 규칙
- 최초 실행에서 처음/마지막과 모든 비고정 항목의 날짜 또는 명시적으로 단조 증가가 보장된 숫자 ID를 비교한다.
- 핀 여부는 목록 어댑터가 알려야 한다. 핀 항목은 순서/연속 기존 항목 판정에서 제외한다.
- 재실행은 새 쪽부터 탐색한다. 연속 N건 또는 비고정 항목 한 페이지가 모두 기존이면 추가 한 페이지 이상을 읽는다.
- 겹침 페이지에서 새 항목을 만나면 중단 후보를 취소하고 겹침 여유를 다시 확보한다.
- 기존 여부는 증분 인덱스뿐 아니라 실제 documents 행도 확인한다. 최근 문서가 로컬에서 사라진 경우 다시 가져온다.
- 신규 항목은 DB 대기 큐에서 날짜/ID 오름차순으로 저장한다. 목록을 모두 확보하기 전에는 저장 순서를 확정하지 않는다.
- 중단/실패 시 탐색 커서 또는 미저장 큐에서 재개한다. 저장 직후 프로세스가 종료되어도 중복 키로 재시도할 수 있다.
- 대용량 최초 수집은 디스크 대기 큐가 필요하다. 전량을 메모리에 적재하지 않으며 정렬 인덱스를 사용한다.
- 재수집에서 정렬이 달라지면 증분을 중단하고 영속적으로 전체 점검 대상으로 낮춘다.

연결한 소스
- HAL 29개: 기존 기관/자료유형 검색 조건을 그대로 사용한다. submittedDate_tdate와 docid로 정렬하며 Solr cursorMark로 재개한다.
  docid는 문자열 필드여서 숫자 최신순으로 취급하면 안 된다. 999999가 5792865보다 앞에 올 수 있다.
  기존 수집기의 external_id(halId 또는 docid)를 보존한다.
- DOAJ: created_date 내림차순. 날짜 경계와 같은 시각의 모든 기수집 ID를 저장해 깊은 page offset을 사용하지 않는다.
  API가 허용하는 명시적 날짜 범위를 사용하며 경계가 무시되면 실패 처리한다.
- NTRS 2개: 영속 전체 탐색 및 페이지 앵커 검증을 연결했다. 실제 API의 최신순이 검증되지 않아 조기 중단을 활성화하지 않는다.
- Generic HTML: incremental.stable_ids, end_selector, newest_params를 명시한 설정에 공통 어댑터를 제공한다.
  선택자에서 0건이 나왔다는 이유만으로 소스 소진으로 처리하지 않는다.
- CERN CDS: 원본은 Anubis 확인 화면. INSPIRE의 CDS ID가 해당 컬렉션과 동등하다는 증거가 없어 증분 지원으로 승격하지 않았다.
- 나머지 1,213개는 목록/안정적인 ID/소진 계약 연결이 필요하다. 정렬 불명 1,229개를 모두 해결한 것은 아니다.
  전체 1,245개에 대해 별도 증분 분류를 산출했으며 현재 30개는 최초 완주 후 활성화 후보, 1,215개는 전체 점검 대상이다.
  정적 분류는 실시간 소스 건강이나 전량 수집 검증을 뜻하지 않는다.

주기적 전체 점검
- LIBERTREE_FULL_CHECK_DAYS: 기본 30일. 0이면 자동 주기 전환을 끈다. 기존 주기 작업에서 incremental을 실행하면 필요 시 full로 전환한다.
- full/backfill은 기존 항목을 포함한 전체 탐색이다. 명시적 소진 후에만 누락 후보를 확정한다.
- 변경 및 누락은 crawl_incremental_changes에 modified/missing으로 기록한다. 수정된 원본 payload를 보존하며 기존 documents를 자동 덮어쓰거나 삭제하지 않는다.
- LIBERTREE_KNOWN_RUN: 기본 50. LIBERTREE_OVERLAP_PAGES: 최소 1, 기본 1.
- LIBERTREE_MAX_PAGES: 작업당 목록 탐색 예산, 기본 200. 예산 소진은 완료가 아니다.
- LIBERTREE_MAX_WALL_S: 기존 작업 시간 예산을 재사용한다.
- 순서/ID/끝 조건을 검증할 수 없는 사이트는 전체 재점검 대상이며 전체 완료 자체를 보장하지 않는다.

스키마와 호환성
- delivery.db.schema.init_delivery_schema의 명시적 migration에 4개 보조 테이블을 추가했다.
- 서비스 시작 시 필수 테이블을 검증한다. 운영 DB에는 migration을 실행하지 않았다.
- 어댑터/검색 범위의 계약이 바뀐 상태를 조용히 재사용하지 않는다. 기존 대기 큐를 보존하고 계약 불일치 오류를 낸다.
- 기존 알려진 항목 경계(CrawlUpToDate)만으로 backfill 완료를 기록하던 워커 동작을 수정했다.

검증과 한계
- 최신순, 오래된 순, 고정 공지, 겹침 중 신규, 목록 예산 중단, 저장 중 실패, DB 재접속, 최근 3건 복구, 정렬 변경, 주기적 수정/누락 점검 테스트.
- 격리 PostgreSQL에서 실제 기본 worker + registry 경로의 최초 부분 저장/재개/완료/재실행과 migration을 검증.
- 실시간 DOAJ는 2026-10-11 14:00~15:00 UTC 범위 24건, HAL CEA는 기존 설정 범위 872건을 사용했다. 글로벌 1,377만/469만 전량 완료로 확대 해석하지 않는다.
- DOAJ: 최초 8 HTTP → 재실행 2 HTTP/저장 0 → 최근 3건 삭제 후 4 HTTP/3건 복구.
- HAL CEA: 최초 10 HTTP → 재실행 2 HTTP/저장 0 → 최근 3건 삭제 후 2 HTTP/3건 복구.
- 두 API는 목록 응답에 상세 메타데이터를 포함하므로 상세 HTTP는 모두 0이다.
- NTRS: 제한 탐색 39 HTTP, 60건 목록 관측, 초기 탐색 미완료. 재실행 효율 검증 성공으로 보고하지 않는다.
- CERN CDS: HTTP 200이지만 접근 확인 화면이며 컬렉션/상세 검증 성공이 아니다.
- HAL의 약 469만 공통 인덱스 수치가 7개 사이트 후보값으로 중복 등장했다. 이를 기관별 독립 건수로 합산하면 안 된다.
  기존 13개 검색 범위 45,286건의 합집합은 44,902 ID: 중복 membership 384건. 전체 HAL 합집합 건수는 미확정이다.
