수집기 검색 API 키 설정 안내

작성일: 2026-10-08 · 대상: Libertree 납품 시스템 운영 담당자

수집·이어받기와 검색 키 설정 — 현재 상황 및 개선 계획 보기

이 문서는 8개 사이트별 검색 API 키의 용도와 적용 방법을 설명합니다. 키 값은 포함하지 않습니다. GPT 번역·요약 키, 시스템 로그인 토큰, ScienceON 인증 설정과는 별개입니다.

이번 배포 후보의 확인 상태
8개 키의 값은 공급사에 보유되어 있습니다. 이번 코드에는 BE·Worker·health 및 검사 하위 프로세스 전달을 반영했습니다. 실제 키 값은 포함하지 않았으며, API 인증 성공·권한·만료·고객 서버 반영은 아직 미검증입니다. 기존 전달본에는 이 전달 설정이 없었습니다.

2. 키가 사용되는 흐름

서버 설정 → 수집 Worker의 환경변수 → 사이트별 검색 API 요청 → 문서 목록·상세 정보 수집

Algolia를 사용하는 7개 수집기는 대상 사이트의 애플리케이션 ID·검색 인덱스와 함께 X-Algolia-API-Key 헤더로 키를 전송합니다. Transparency 수집기는 대상 Azure Search 서비스에 api-key 헤더로 전송합니다. 문서 목록을 검색하는 용도이며, 이 키만으로 PDF 다운로드·텍스트 추출 성공까지 보장되지는 않습니다.

수집기 설정 예시는 이 키들을 공개 읽기 전용 검색 키로 분류합니다. 실제 보유 키의 권한은 별도 확인이 필요합니다. 대상 사이트 서비스에 맞는 키를 사용해야 하며, 고객이 별도 Algolia·Azure 계정을 만들어 발급한 키로 대체할 수 없습니다. 두 변수가 같은 기관을 가리키더라도 임의로 같은 값을 넣지 않습니다.

3. 기존 납품본의 설정 상태

  • crawler/.env.example에 8개 변수 이름이 있으며 값은 비어 있습니다. 실제 .env는 기존 압축파일에 포함되지 않았습니다.
  • delivery/.env.example와 기본 docker-compose.yml에는 이 8개 키의 Worker 전달 설정이 없습니다.
  • 호스트의 crawler/.env 또는 delivery/.env에 값을 기록하는 것만으로 납품 Worker 컨테이너에 자동 전달되지 않습니다.
  • 수집기 모듈이 로딩될 때 환경변수를 읽으므로, 값을 변경하면 Worker 컨테이너를 새 설정으로 재생성해야 합니다.

4. Docker 적용 절차

아래는 고객 환경에 적용할 때 사용할 예시입니다. 현재 서버 설정을 변경한 것은 아닙니다. 기존 delivery/.env의 DB·인증·저장소 설정은 유지하고 아래 항목을 추가합니다. 실제 값은 공급사와 합의한 별도 전달 경로로 받아 입력합니다.

CANCER_FR_CATALOGUE_DES_PUBLIC_KEY=
EDUCATION_GOVT_NZ_OUR_WORK_KEY=
EDUCATION_GOVT_NZ_SEARCH_KEY=
INRAE_FR_ACTUALITES_KEY=
NKVTS_NO_ENGLISH_KEY=
PHFSCIENCE_NZ_DIGITAL_LIBRARY_KEY=
PHFSCIENCE_NZ_NEWS_PUBLICATIONS_KEY=
TRANSPARENCY_GOV_AU_PUBLICATIONS_KEY=

이번 버전의 기본 Compose에 키 전달 설정이 포함되어 있습니다. 별도의 keys 오버라이드를 만들 필요는 없습니다. 실행 중 작업을 정리하고 DB·파일 백업 후, 새 코드로 마이그레이션하고 서비스를 갱신합니다. 저장소 루트 기준:

docker compose --env-file delivery/.env -f delivery/docker-compose.yml --profile tools run --rm --build migrate
docker compose --env-file delivery/.env -f delivery/docker-compose.yml up -d --build --force-recreate be fe worker file-worker

기존 호스트 PDF 저장소를 사용하면 두 명령 모두 -f delivery/docker-compose.blob.yml을 추가하고 기존 프로젝트명·볼륨 설정을 유지합니다. health 사용 시 delivery/docker-compose.health.yml을 함께 지정해 health 서비스도 재생성합니다. 키만 교체할 때는 BE·Worker 및 사용 중인 health 재생성이 필요합니다.

5. 설정값을 노출하지 않는 확인

Worker에서 다음 명령을 실행하면 값 대신 설정 여부만 표시합니다. 아래 명령도 운영 환경의 기존 Compose 파일 조합을 유지해 사용합니다.

docker compose --env-file delivery/.env -f delivery/docker-compose.yml exec -T worker python - <<'PY'
import os
keys = (
    "CANCER_FR_CATALOGUE_DES_PUBLIC_KEY",
    "EDUCATION_GOVT_NZ_OUR_WORK_KEY",
    "EDUCATION_GOVT_NZ_SEARCH_KEY",
    "INRAE_FR_ACTUALITES_KEY",
    "NKVTS_NO_ENGLISH_KEY",
    "PHFSCIENCE_NZ_DIGITAL_LIBRARY_KEY",
    "PHFSCIENCE_NZ_NEWS_PUBLICATIONS_KEY",
    "TRANSPARENCY_GOV_AU_PUBLICATIONS_KEY",
)
for key in keys:
    print(key, "설정됨" if os.environ.get(key, "").strip() else "미설정")
PY

이 검사는 환경변수 존재 여부만 확인합니다. API 인증 성공 검사는 별도입니다. 실제 값을 출력하는 printenv, 전체 docker inspect, 렌더링된 Compose 설정을 고객 회신 자료에 첨부하지 않습니다.

6. 동작 확인과 납품 판정

  1. 수집기별 검색 API에서 인증이 성공하고 정상 형식의 응답이 오는지 확인합니다. HTTP 200이라도 응답 내용과 대상 목록을 확인합니다.
  2. 시험용 DB에서 FE로 소량 수집을 실행하고, 검색 결과·문서 저장·중복 처리 결과를 각각 확인합니다. 운영 FE 실행은 실제 작업을 등록하므로 단순 연결 검사와 구분합니다.
  3. Cancer FR은 HTML 경로 성공과 Algolia 보조 경로 인증 성공을 별도 기록합니다. HTML 수집 성공만으로 키가 유효하다고 판정하지 않습니다.
  4. PDF 주소가 있는 샘플은 실제 파일 저장까지 별도로 확인합니다. 검색 키 검증과 PDF 검증은 다른 항목입니다.

health 컨테이너와 검사 하위 프로세스 허용 목록에 8개 키를 연결했습니다. 더미 값으로 전달 구성을 검사했으며, 실제 사이트 인증 성공으로 판정한 것은 아닙니다. health 표본 수집의 성공도 전체 사이트 수집 완료를 뜻하지 않습니다.

7. 납품 시 함께 확인할 기록

각 수집기별로 키 보유 여부 / 고객 Worker 전달 여부 / API 인증 결과 / 소량 문서 저장 결과 / PDF 결과 / 검증 일시·코드 버전을 기록합니다. 현재 8개 키 모두 공급사 보유 확인 상태이며, 고객 환경 적용과 실제 API 검증 결과는 미확인입니다. 실제 키 값, 키가 포함된 요청 헤더·명령줄·로그는 본 문서에 포함하지 않습니다.

근거: 기존 전달 압축파일의 설정 예시·Compose 구성과 8개 수집기 소스, 현재 작업 코드의 health 검사 환경변수 전달 경로를 확인했습니다.
