1.개요

본 문서는 Libertree — 웹페이지 데이터 수집·분석·요약 서비스(계약상 명칭: 웹 게시글 수집·메타정보화 및 AI 요약 시스템)의 상세 기능정의서이다. 약 2,000개 URL에 산재한 웹 게시글의 메타정보를 수집·구조화하고, 첨부파일을 수집하여 텍스트를 추출한 뒤, AI 기반 자동 요약을 생성하여 검색·활용 체계를 마련하는 것을 목적으로 한다.

기능 정의의 기준은 요구사항분석서(REQ-2026-001)의 기능 요구사항 FR-01 ~ FR-10 및 데이터베이스 요구사항이다. 각 기능에 대해 기능명·상세 설명·입력·처리·출력/저장·관련 화면·우선순위와 함께, 현재 구현 시스템에 대한 감사 결과에 근거한 구현 상태를 병기한다.

구현 상태 표기는 다음 세 단계로 구분한다.

  • 구현 — 요구사항이 실제로 동작하는 형태로 구현되어 운영 데이터에서 확인됨
  • 부분 — 핵심 흐름은 동작하나 요구된 범위·형태의 일부가 미충족
  • 미구현 — 요구된 동작이 실제로 연결·동작하지 않음(헬퍼/골격만 존재하는 경우 포함)
본 문서에 표기된 채움률·건수·엔진 정보는 별도 구현 감사 세션에서 확인된 실측치이며, 계약서(요구사항분석서)의 명세와 실제 구현이 다른 항목은 5. 구현 현황 종합의 계약 대비 변경점에 정리한다.

요구사항분석서 4장 기능 요구사항(FR-01 ~ FR-10)의 전체 목록과 우선순위, 그리고 현재 구현 상태를 요약한다.

3.기능별 상세

FR-01 · URL 수집 및 메타정보 추출 구현

기능명URL 수집 및 메타정보 추출
상세 설명크롤러가 지정된 URL 목록을 순회하며 게시글의 제목·작성일·게시일·저자·기관·저널·키워드·초록·메타정보URL을 수집하여 documents 테이블에 저장한다.
입력대상 URL 목록(약 2,000개 사이트 게시판 URL), 사이트별 게시판 구조 정의
처리사이트 순회 → 목록/상세 페이지 파싱 → 서지 메타필드 추출(정적·동적 페이지 모두) → 정규화 후 저장
출력/저장documents 테이블의 문서정보 컬럼(title, author, publisher, published_journal, written_at, posted_at, keywords, abstract, metadata_url 등)
관련 화면수집 관리 / 목록·상세 화면(FR-06, FR-08)에서 결과 확인
우선순위필수
구현 상태구현 — 실측 채움률: 제목(title) 100% · 게시일(posted_at) 98% · 기관(publisher) 96% · 초록(abstract) 100% · 키워드(keywords) 60% · 저자(author) 49% · 저널(published_journal) 15%. 핵심 서지필드는 높은 채움률로 수집되며, 저자·저널은 원본 페이지에 정보가 없는 경우가 많아 상대적으로 낮다.

FR-02 · 증분 수집 (이어 수집) 미구현

기능명증분 수집 (이어 수집)
상세 설명수집 재실행 시 사이트별 max(post_no)를 조회하여 이미 수집된 게시글은 건너뛰고 신규 게시글만 수집한다. 글번호가 없는 사이트는 metadata_url 기준으로 중복을 판별한다.
입력사이트별 마지막 수집 글번호(워터마크), 재수집 대상 URL
처리사이트별 max(post_no) 조회 → 워터마크 이후 신규 글만 순회 → 기존 글 스킵
출력/저장신규 게시글만 documents에 추가 저장(중복 미저장)
관련 화면수집 관리 화면(재수집 트리거)
우선순위필수
구현 상태미구현 — max(post_no) 기반 워터마크 로직이 실제 수집 흐름에 연결되어 있지 않다(관련 헬퍼 함수만 존재). 재실행 시에는 insert 시점의 dedup(중복 삽입 방지)만 동작하므로, 이미 수집된 페이지를 다시 순회한 뒤 저장 단계에서 걸러내는 방식이어서 "스킵을 통한 이어 수집" 요구는 충족하지 못한다.

FR-03 · 첨부파일 다운로드 부분

기능명첨부파일 다운로드
상세 설명PDF·HWP·DOCX·XLSX 등 첨부파일을 자동 다운로드하여 12자리 번호 기반 폴더 구조(data/0000/0000/)에 저장한다. 원본 파일명은 original_filename 컬럼에 별도 보관한다.
입력게시글의 첨부파일 다운로드 URL(file_url), 레코드 고유번호(sequence)
처리다운로드 URL 요청 → 12자리 0채움 파일명 산출 → 계층형 폴더에 저장 → 경로·원본명 기록
출력/저장블랍 저장소의 원본 파일, stored_filename · file_path · original_filename 컬럼
관련 화면목록/상세 화면의 첨부파일 링크(FR-06, FR-08), 모니터링(FR-09)
우선순위필수
구현 상태부분 — PDF 다운로드와 original_filename 보관은 정상 동작한다. 다만 다운로드 URL을 게시글당 1개(pdf_url)만 수용하고 저장 확장자를 .pdf로 고정하므로, 요구된 HWP·DOCX·XLSX 등 다중 포맷·복수 첨부는 온전히 처리하지 못한다.

FR-04 · 텍스트 추출 구현

기능명텍스트 추출 (계약상 Docombu)
상세 설명첨부파일에서 텍스트를 추출하고, 원본과 동일한 파일명(.txt 확장자)으로 같은 폴더에 저장한다. 추출 경로는 extracted_text_path에 기록한다.
입력다운로드된 첨부파일(원본 PDF 등), 저장 경로
처리파일 포맷 판별 → 텍스트 추출 → 원본과 동일 파일명의 .txt로 같은 폴더에 co-located 저장 → 경로 기록
출력/저장추출 텍스트 .txt 파일, extracted_text_path 컬럼
관련 화면상세 보기의 추출 텍스트(FR-08), 모니터링 추출 건수(FR-09)
우선순위필수
구현 상태구현 — 총 288,124건(전체의 59.8%)에서 텍스트를 추출하여 원본과 같은 폴더에 .txt로 저장한다. 단, 실제 사용 라이브러리는 계약상 명시된 Docombu가 아니라 pdfplumber · PyPDF2 · olefile 조합이다(계약 대비 변경점 참조).

FR-05 · AI 요약 생성 구현

기능명AI 요약 생성 (계약상 OpenAI API)
상세 설명추출된 텍스트를 AI 모델에 전달하여 자동 요약을 생성하고 summary 컬럼에 저장한다. 처리 상태는 summary_status(pending / done / failed)로 관리한다.
입력추출 텍스트(extracted_text_path의 내용)
처리텍스트 로드 → 요약 엔진 호출 → 한국어 요약 생성 → 결과·상태 기록(실패 시 failed)
출력/저장summary 컬럼(DB 저장, 별도 파일 미생성), summary_status 컬럼
관련 화면목록의 요약 미리보기(FR-06), 상세 보기(FR-08), 모니터링 요약 건수(FR-09), 재처리(FR-10)
우선순위필수
구현 상태구현 — 총 66,248건(전체의 13.8%)에 대해 요약이 생성되었다. 실제 요약 엔진은 계약상 OpenAI가 아니라 로컬 Ollama이며, gemma4:26b(약 55%)와 qwen3:8b(약 45%)를 사용한다. OpenAI 연동 코드는 존재하나 프로덕션에서는 사용하지 않는다.

FR-06 · 관리자 화면 — 목록 조회 부분

기능명관리자 화면 — 목록 조회
상세 설명수집된 레코드를 목록(스크롤/페이지네이션)으로 표시한다. 요구 표시 항목: 레코드번호·제목·저자·기관·게시일·메타정보URL·요약 미리보기·첨부파일 링크.
입력목록 조회 요청(페이지·정렬 조건)
처리DB 조회 → 페이지네이션/스크롤 렌더링 → 컬럼 표시
출력/저장레코드 목록 화면(조회 전용)
관련 화면finolaw 관리자 목록 화면
우선순위필수
구현 상태부분 — finolaw에 목록 화면 2종이 존재한다. 다만 단일 화면에서 요구된 컬럼 전체(특히 저자·기관·메타정보URL·첨부파일 링크)를 한 번에 표시하지 못해, 요구 항목이 화면별로 분산되어 있다.

FR-07 · 관리자 화면 — 검색·필터 부분

기능명관리자 화면 — 검색·필터
상세 설명제목·저자·키워드·기간(게시일)·사이트·요약 처리 상태 기준으로 검색 및 필터링 기능을 제공한다.
입력검색어 및 6개 필터 조건(제목/저자/키워드/기간/사이트/요약상태)
처리조건 조합 → DB 질의 → 결과 목록 반환
출력/저장필터링된 레코드 목록 화면
관련 화면finolaw 검색/필터 화면
우선순위필수
구현 상태부분 — 요구된 6개 필터 차원이 모두 존재하나 2개 화면에 분산되어 있어, 요약 처리 상태를 키워드·기간과 한 화면에서 함께 결합해 필터링하는 것은 불가능하다.

FR-08 · 관리자 화면 — 상세 보기 구현

기능명관리자 화면 — 상세 보기
상세 설명레코드 선택 시 전체 메타정보·추출 텍스트·AI 요약·첨부파일 다운로드 링크를 상세 화면에 표시한다.
입력레코드 선택(문서 ID)
처리단일 레코드 조회 → 메타/요약/첨부 정보 렌더링
출력/저장문서 상세 화면(조회 전용)
관련 화면finolaw 문서 상세 화면
우선순위필수
구현 상태구현 — finolaw 문서 상세 화면에서 전체 메타정보 · AI 요약 · 첨부파일 다운로드를 모두 제공한다.

FR-09 · 수집 현황 모니터링 구현

기능명수집 현황 모니터링
상세 설명사이트별 수집 건수·미처리 요약 건수·오류 발생 건수를 관리자 대시보드에서 확인할 수 있다.
입력집계 조회 요청
처리사이트별 수집/다운로드/추출/요약 건수 집계 → 진행률 산출 → 오류 집계
출력/저장대시보드 현황 화면(집계 지표)
관련 화면finolaw 대시보드
우선순위권장
구현 상태구현 — 사이트별 수집·다운로드·추출·요약 건수와 진행률, 그리고 오류(PDF 처리 실패) 현황을 대시보드에서 제공한다.

FR-10 · 재처리 기능 부분

기능명재처리 기능
상세 설명텍스트 추출 실패 또는 AI 요약 실패 건을 관리자가 수동으로 재실행할 수 있는 기능을 제공한다.
입력재처리 대상 레코드 선택(관리자 조작)
처리선택 레코드에 대해 추출/요약 파이프라인 재실행
출력/저장갱신된 summary / extracted_text_path 및 상태
관련 화면finolaw 상세/관리 화면의 재처리 버튼
우선순위권장
구현 상태부분 — AI 재요약만 지원한다. 텍스트 추출 실패 건에 대한 추출 재처리 버튼은 없어, 추출 단계 재실행은 관리자 화면에서 수동으로 수행할 수 없다.

5.구현 현황 종합

기능 요구사항 10건에 대한 최종 구현 집계는 다음과 같다.

  • 구현 6건 — FR-01(메타추출) · FR-04(텍스트추출) · FR-05(AI요약) · FR-08(상세보기) · FR-09(모니터링) + FR-01 계열 핵심 파이프라인
  • 부분 3건 — FR-03(첨부 다운로드) · FR-06(목록 조회) · FR-07(검색·필터) · FR-10(재처리)

계약 대비 변경점
구현 시스템은 계약서(요구사항분석서)의 여러 기술 명세를 등가의 로컬 구성으로 대체하여 구축되었다. 주요 변경점은 다음과 같다.
  • 텍스트 추출 라이브러리: 계약상 Docombu → 실제 pdfplumber · PyPDF2 · olefile 조합(FR-04)
  • AI 요약 엔진: 계약상 OpenAI API → 실제 로컬 Ollama(gemma4:26b + qwen3:8b). OpenAI 코드는 존재하나 프로덕션 미사용(FR-05)
  • 인프라·저장소: 계약상 PostgreSQL(RDS) · S3 · AWS(EC2/ECS) → 실제 로컬 단일 호스트의 SQLite 단일 파일 DB + 로컬 디스크 블랍 저장소. 계약의 data/AAAA/BBBB/ 12자리 계층 저장 규칙은 로컬에서 그대로 유지
