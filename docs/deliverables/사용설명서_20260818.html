1시스템 구성

네 개의 컨테이너가 Docker Compose로 함께 돕니다.

구성요소역할
콘솔(FE)브라우저 화면. 수집 시작·진행 확인·스케줄 관리 (기본 http://127.0.0.1:3000)
API(BE)콘솔과 외부 도구가 쓰는 REST API (기본 http://127.0.0.1:8080)
워커큐에서 작업을 하나씩 꺼내 실제 크롤을 수행. 한 번에 하나(직렬)
PostgreSQL문서 메타데이터·작업 큐·수집 진도. PDF 원본은 별도 blob 볼륨에 저장

크롤러는 사이트당 하나씩 총 804개가 소스에 포함되어 있으며, 콘솔에서 사이트를 골라 작업을 등록하면 워커가 해당 크롤러를 실행합니다.

2최초 설치

  1. 소스 번들을 풀고 리포지토리 루트에서 delivery/.env를 만듭니다 (delivery/.env.example 복사 후 수정).
  2. 비밀값 두 개를 채웁니다 — 비워 두면 시작을 거부합니다: 
    # POSTGRES_PASSWORD: 원하는 DB 비밀번호
# DELIVERY_API_TOKEN: 아래 명령으로 생성
openssl rand -hex 32
  3. 최초 1회 부트스트랩(스키마 생성 → 기동): 
    docker compose -f delivery/docker-compose.yml --profile bootstrap run --rm --build migrate && \
docker compose -f delivery/docker-compose.yml up -d
  4. 콘솔 접속 → 우측 상단에 API 토큰 입력 → 화면이 데이터를 보여주면 완료입니다.
업그레이드(새 소스 반영) 때도 같은 migrate 명령을 먼저 실행하세요. --build가 반드시 필요합니다 — 없으면 낡은 이미지가 옛 스키마로 조용히 통과할 수 있습니다.

3데이터 복원 (전달받은 DB·PDF)

데이터는 소스와 별도로 전달됩니다: PostgreSQL 덤프(.dump, pg_dump -Fc 형식)와 PDF 디렉터리(blob) 두 가지입니다.

  1. DB 복원 — 2절의 부트스트랩을 마친 뒤: 
    docker compose -f delivery/docker-compose.yml exec -T postgres \
  pg_restore -U libertree -d libertree --no-owner /tmp/libertree.dump
    (덤프 파일을 먼저 컨테이너로 복사: docker cp libertree.dump <postgres컨테이너>:/tmp/)
  2. PDF 복원 — 전달받은 blob 디렉터리를 구조 그대로 blob 볼륨 경로에 넣습니다.
    중요: {루트}/{앞4자리}/{다음4자리}/{12자리번호}.pdf 디렉터리 구조 자체가 색인입니다. 파일을 평평하게 풀거나 이름을 바꾸면 문서와 PDF의 연결이 끊어집니다. rsync -a로 통째로 복사하세요.
  3. 검증: 콘솔의 수집 상태 화면에서 문서 수가 전달 명세서의 수와 일치하는지 확인합니다.

4일상 운영 — 콘솔 사용법

화면하는 일
수집사이트를 골라 수집 작업을 등록하고, 진행 중 작업을 보고, 취소합니다
크롤러 상태804개 크롤러의 건강 상태 목록
백필대형 사이트의 장기 수집 진행률 (5절)
수집 상태DB에 쌓인 문서 통계
스케줄사이트별 주기 수집 예약 (예: 24시간마다)

수집 모드 세 가지

모드용도
incremental평소 사용. 이미 있는 문서는 건너뛰고 새 문서만 저장. 최신순 사이트는 이미 받은 구간을 만나면 자동으로 일찍 끝납니다
full전체 재순회 (문서 갱신 반영이 필요할 때만)
backfill대형 사이트를 여러 조각에 걸쳐 끝까지 받기 — 5절 참고

「부분 수집」 배지

완료된 작업 옆에 부분 수집 배지가 붙으면, 그 실행이 시간 예산(기본 25분, LIBERTREE_MAX_WALL_S)에 걸려 남은 페이지를 건너뛰었다는 뜻입니다. 저장된 문서는 유효합니다. 같은 자리에서 반복해서 잘리면 그 사이트는 backfill 모드로 돌리세요.

5대형 사이트 백필 (이어서 수집)

10만 건이 넘는 사이트 25곳(최대: doaj-org-search 약 1,337만 건)은 한 번의 실행으로 끝나지 않습니다. backfill 모드는 어디까지 걸었는지 저장하고, 잘리면 자동으로 다음 조각을 큐에 넣어 결국 완주합니다.

시작하기

  1. 최초 1회, 진행률 표시용 총량을 시드합니다 (리포지토리 루트에서): 
    python3 delivery/scripts/seed_backfill_estimates.py
  2. 사이트별로 백필 시작: 
    curl -X POST "http://127.0.0.1:8080/jobs" \
  -H "Authorization: Bearer $DELIVERY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"site_id": "doaj-org-search", "mode": "backfill"}'
  3. 이후는 자동입니다. 콘솔 백필 화면에서 진행률을 확인하세요.

체인이 멈추는 세 가지 경우

표시의미와 대응
완주크롤러가 목록 끝에 도달했다고 확인함. 정상 종료 — 할 일 없음
stalled 경고실행됐지만 진도가 나가지 않음(사이트 차단·구조 변경 의심). 작업 상세의 원문 로그 확인 후, 해결되면 backfill을 다시 등록하면 저장된 지점부터 이어갑니다
취소운영자가 취소하면 체인이 멈춥니다. 커서는 남아 있으므로 다시 등록하면 이어갑니다
백필 조각 사이사이에 다른 사이트의 작업이 정상적으로 끼어 돕니다 — 한 사이트가 큐를 독점하지 않습니다. doaj 완주는 조각 1,300여 개, 수 주가 걸리는 것이 정상입니다.

6문제가 생겼을 때

증상확인·조치
콘솔 "연결 안 됨"docker compose -f delivery/docker-compose.yml ps로 be가 떠 있는지, 토큰이 올바른지 확인
BE가 시작 거부로그에 이유가 적혀 있습니다. 대개 DELIVERY_API_TOKEN 미설정(32자 미만)이거나 스키마 미적용(2절 migrate)
신규 저장 0건이 계속"새 문서가 없는 날"일 수도, 차단일 수도 있습니다. 작업 상세의 크롤러 원문 로그에서 403·차단 문구를 확인하세요
백필이 의심스럽게 일찍 완주일부 사이트는 페이지 구조가 바뀌면 빈 목록으로 읽힐 수 있습니다(mof·uchile·etera·adruk). 사이트를 브라우저로 열어 확인 후 backfill 재등록 — 커서가 자동으로 미완주로 돌아갑니다
워커가 죽음/재시작 반복docker compose ... logs worker 확인. 워커는 자동 재시작되며, 진행 중이던 작업은 복구 절차가 다시 큐에 넣습니다
