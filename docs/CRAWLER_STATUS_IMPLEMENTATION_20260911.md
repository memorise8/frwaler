# 수집기 현황 구현 및 추가 진단 결과 — 2026-09-11

현재 `libertree` 브랜치의 운영 콘솔에 **`/status` 화면과 `GET /crawler-status` API**를 구현했다. 검사 기록과 실제 작업 이력을 별도로 보여준다. 운영 배포와 무제한 수집은 실행하지 않았다.

## 구현된 기능

- 1,243개 검사 대상 식별자의 검색, 검사 상태 필터, 30개씩 페이지 이동.
- 최근 운영 결과 필터: 종료 기록 없음 / 최근 실패 / 저장 확인 / 신규 0건 원인 미확인 / 취소.
- 최신 작업 상태와 대기·실행 중·중지 요청 작업 수를 별도 표시.
- 최근 종료 시각·신규 저장 건수·오류, 마지막 저장 성공 시각·건수 표시.
- 검사일·검사 오류·코드 파일·저장 표본의 제목과 원문 링크 표시.
- 화면이 보이는 동안 30초마다 운영 이력 갱신, 수동 새로고침.
- BE 조회 불가는 ‘실행 기록 없음’ 또는 ‘0건’으로 바꾸지 않는다. 검사 기록은 그대로 조회 가능하다.
- 이전 성공 후 최신 실패가 발생한 경우 최신 실패를 우선 표시한다. 과거 성공은 마지막 성공 항목에만 남긴다.

BE는 `crawl_jobs`를 읽으며 운영 작업을 등록하거나 수집기를 실행하지 않는다. 출처별 최근 작업·종료·저장 성공 및 현재 작업 수를 조회한다. 현재 브랜치 DB 초기화에 조회용 인덱스 두 개를 추가했다. `/crawler-status?site_id=...`로 단일 수집기를 조회할 수도 있다.

## 연결과 적용

운영 콘솔의 `BE_URL`을 같은 배포 환경의 BE 주소로 지정해야 한다. 기본값은 `http://127.0.0.1:8080`이다. FE와 BE가 별도 컨테이너라면 컨테이너 네트워크의 BE 서비스 주소를 사용한다. BE는 기존 방식대로 `init_delivery_schema()`를 실행해 인덱스를 반영한다. 프런트엔드는 `delivery/fe`에서 `npm ci`, `npm run build`, `npm run start`로 실행한다.

검사 데이터는 `delivery/fe/src/content/crawler-checks.json`에 포함했다. `scripts/audit/export_crawler_status_preview.py`의 `--console-output` 옵션으로 갱신할 수 있다. 입력 `--runs`는 오래된 검사부터 최신 검사 순서로 제공하며, 출력된 데이터는 FE 빌드에 포함된다. 검사 기록 자체를 새로고침할 때는 데이터 갱신과 FE 재빌드가 필요하다. 운영 이력 조회는 이 정적 검사 파일과 독립적으로 갱신된다.

현재 체크아웃과 별도 납품 브랜치는 구조가 다르다. 이번 구현은 현재 브랜치에 적용했고, 다른 브랜치나 실제 서비스 컨테이너를 덮어쓰지 않았다. 새 `/status`는 운영 콘솔 메뉴에서 접근하며, 기존 8월 카탈로그 화면도 유지한다.

## 추가 수집기 진단

### BFE 출판물 DB 복구

`bfe-admin-ch-bfe`의 기존 BFE exturl 주소는 유효하지 않았지만 `https://pubdb.bfe.admin.ch/de/suche`는 실제 출판물 목록을 반환했다. 직접 목록 요청과 직접 다운로드 링크 해석으로 변경했다. 알려진 빈 검색 결과 문구가 아닌데 문서 항목도 없는 응답은 예외로 보고해, 오류 페이지를 ‘자료 없음’으로 처리하지 않도록 했다.

- 임시 SQLite에서 표본 3건 저장.
- 직접 목록 1·2페이지의 서로 다른 출판물 ID 확인.
- BFE 설명문은 기존 구현이 제목·날짜·언어·파일 크기를 조합한 메타데이터 설명이며 PDF 본문 요약이 아니다.
- 새 표본 결과를 콘솔 검사 파일에 반영했다.

### ETH 접근 제한 확인

`research-collection-ethz-ch-search`는 API 루트가 JSON을 반환하지만 실제 필터 검색 URL은 `Access Restricted` HTML을 반환했다. 이 환경에서는 현재 검색 결과를 정상 JSON으로 확인하지 못했다. 접근 제한을 해결한 것으로 표시하거나 다른 범위의 문서로 대체하지 않았다. 마지막 검사 분류는 보수적으로 미확인 상태를 유지한다.

NHC 502, TLS 연결 실패 및 다른 빈 목록 출처는 별도 진단 대상으로 남아 있다.

## 검증

- 상태 API·기존 BE·작업 큐·워커 테스트 **16개 통과**. 실제 전용 임시 PostgreSQL 사용.
- BFE 회귀·기존 수집기 복구·검사 상태 집계 테스트 **18개 통과**.
- 프런트엔드 typecheck, lint, production build 통과.
- 브라우저에서 실제 테스트 BE·PostgreSQL과 연결해 ‘과거 성공 → 최근 실패 → 새 작업 대기’ 표시 확인.
- 테스트 BE를 중지한 뒤 조회 불가 표시, 운영 필터 비활성화, 검사 목록 유지 확인.
- 모바일 390px에서 가로 넘침 없음, JavaScript 오류 없음 확인.

검사 로그: `scripts/audit/out/status_implementation_20260911/`, BFE 결과: `scripts/audit/out/overnight_20260911/`. 사용한 DB와 서버는 테스트용이며 운영 데이터는 수정하지 않았다.

## 실제 의미와 남은 한계

‘실행 중’은 현재 DB의 작업 큐 상태다. 현재 브랜치에는 독립적인 heartbeat 조회가 없어 실제 프로세스 생존을 확정하지 않는다. 전체 작업 로그와 실행별 발견·갱신·중복 수까지 표시하는 기능은 이번에 구현하지 않았다. 작업 신규 저장 수는 기존 워커의 계산 방식을 사용한다.

일부 수집기는 내부 오류를 출력한 뒤 0을 반환한다. 따라서 신규 0건은 성공·자료 없음으로 단정하지 않는다. 구조화된 실패 원인과 heartbeat를 수집기·워커에 추가하면 후속으로 더 정확히 구분할 수 있다.

검사 파일은 서로 다른 코드 버전과 제한 조건에서 실행한 최근 기록을 모은 것이다. 현재 코드의 전량 정상률이 아니다. 표본 성공과 전체 기간·전체 원문의 수집 완료도 구분한다. 자동 주기 검사나 장시간 무인 운영 수집은 이번 작업에서 예약하지 않았다.
