공통 증분 연결 배치 운영 (2026-10-12 시작)

현재 goal은 전체 수집기 전수 대조가 아니라 등록 수집기의 공통 증분 연결 또는 근거 있는 불가 분류다.
대용량 및 납품 대상부터 처리한다. 단순히 어댑터가 아직 없다는 이유로 완료 분류하지 않는다.
각 배치는 코드 단위테스트, 새 격리 DB 재실행 요청 측정, 커밋, progress.json/사이트 대장 기록을 포함한다.
운영 DB 변경, 배포, 외부 발송 및 원문 데이터 삭제는 하지 않는다.

큐
python -m delivery.scripts.incremental_rollout --base <기존 plan-dev 결과 경로>
python -m delivery.scripts.incremental_rollout --base <결과 경로> --review <배치 review.json>
pending은 구현/검토 대상, connected는 공통 실행 경로 연결, classified는 증거와 사유가 있는 full_rescan_required다.
connected도 전 세계 소스 전량 수집 완료를 뜻하지 않는다. 최초 완주 전에는 baseline_complete를 지정하지 않는다.

Batch 001: Federal Register HHS (기존 관측 범위 109,548건)
- 기존 날짜 분할 및 다음 페이지 URL 검증을 재사용한다.
- 날짜 범위를 최신 쪽부터 분할하고, 각 작은 구간의 실제 건수/끝/원문 ID를 검증한다.
- API의 10,000 표시 상한은 전체 건수로 오인하지 않는다. 구간별 실측 합계와 일치 여부를 따로 검증한다.
- 문서 번호 재사용이 있어 번호+원문 URL을 식별키로 사용한다.
- 짧거나 빈 초록도 원문 그대로 저장한다. 기존 길이 제외나 분량을 늘리는 문장 보충은 적용하지 않는다.
- 구간 분할만 한 체크포인트는 소스 소진도, 겹침 한 페이지를 읽은 것도 아니다.
- 기존 HAL/DOAJ 계약 해시는 새 배치 등록 때문에 바뀌지 않도록 별도 registry 확장 경로를 쓴다.
- 공용 RequestGate(delay=1.5), 단일 시도, 자동 리다이렉트 금지, 429 cooldown, 실제 요청 로그를 사용한다.
- 2026-09-28~2026-10-02의 HHS 48건 실시간 범위: 최초 목록 요청 10회/3건 저장,
  중단 후 재개 0회/45건 저장, 재실행 4회/신규 0건. 기존 문서 행은 그대로 유지했다.
- 별도의 새 PostgreSQL DB에서 실제 기본 worker/registry를 통해 3건→12건→12건을 검증했다.
  PostgreSQL 검증은 통제된 응답 fixture이며 실시간 요청 측정은 앞의 48건 검증이다.

실행
python -m delivery.scripts.measure_incremental_batch --out <새 출력 경로> --gate-dir <공용 request-gate 경로> --lower YYYY-MM-DD --upper YYYY-MM-DD
이 명령은 기존 경로를 덮어쓰지 않고 새 SQLite DB를 만든다. 문서 삭제 없이 부분 저장, 재개, 재실행을 측정한다.
INCREMENTAL_ROLLOUT_TEST_DSN을 쓸 때는 비어 있는 incremental_rollout_ 접두사의 전용 PostgreSQL DB를 사용한다.
테스트는 기존 테이블을 truncate/drop하지 않으며 기존 documents 테이블이 있으면 실행하지 않는다.

Batch 002: Nemertes (기존 5개 browse 범위 합계 26,521건)
- 기존 title/items endpoint의 dateaccessioned,desc 정렬을 사용한다. discovery/search/objects는
  같은 scope에서도 49건 대신 87건을 반환했으므로 기존 납품 범위를 대체하지 않는다.
- 대표 49건 범위에서 기존 제목순과 날짜순의 UUID 집합 일치 및 날짜 내림차순을 관측했다.
- 5개 범위의 머리 항목을 모두 읽은 뒤 날짜순으로 합친다. 한 범위에서 기존 항목을 만났다는
  이유만으로 아직 확인하지 않은 다른 범위의 새 항목을 건너뛰지 않는다.
- 최초 전체 목록 완주 시 공통 엔진이 실제 순서를 판별한다. UUID, 날짜, 페이지 건수,
  이전 페이지 fingerprint와 페이지 간 순서를 검사하고 변경 시 완료 판정을 중단한다.
- 목록 버퍼와 합치기 커서를 DB에 저장하고, 전체 목록 발견 후 오래된 것부터 저장한다.
- 짧거나 빈 초록은 그대로 보존한다. 상세 요청은 bundle 메타데이터에 한정하고 PDF 본문은
  다운로드하지 않는다. bundle/bitstream 추가 페이지가 관측되면 검토 필요 오류를 낸다.
- 재현: python -m delivery.scripts.measure_nemertes_incremental --out <새 경로> --gate-dir <공용 gate>
  원래 5개 중 49건의 한 범위만 실측한다. 전체 26,521건 대조를 수행했다는 의미가 아니다.
- 실측 결과: 최초 부분 저장 8회 요청/3건 저장, 재개 46회/46건 저장, 재실행 3회/0건 저장.
  재개 시 목록 재요청 0회, 재실행 시 상세(bundle) 조회 0회이며 기존 문서 행은 동일했다.
  저장된 49개 UUID는 기존 제목순 전체 응답과 일치하고 저장 순서는 accession 날짜 오름차순이다.
- tests.test_incremental_dspace_worker는 새로운 incremental_rollout_ PostgreSQL DB에서
  기본 worker를 검증한다. 5개 범위를 날짜순으로 합친 fixture이며 실시간 관측과 구분한다.

Batch 003: AMOLF·KRIVET 증분 보류 분류
- 보존된 AMOLF 380페이지/7,593개 URL과 KRIVET 874페이지/8,715개 목록 행의 해시를 검증했다.
  이는 이미 확보한 원문 재분석이며, 전체 수집을 새로 수행하거나 전수검증 goal을 재개한 것이 아니다.
- AMOLF의 목록 항목에는 datetime이 없고 인용문 연도와 URL slug로는 같은 연도 내 순서를
  판별할 수 없다. 기존 목록 selector는 현재 첫 페이지의 20건 중 0건을 찾는다.
  full_rescan_required는 증분 중단을 허용하지 않는 분류다. 기존 파서 정상이나 전체 수집 가능
  판정을 뜻하지 않으며, AMOLF 목록 파서 수리는 별도 미해결 사항으로 남는다.
- KRIVET 메뉴 19·23은 보존된 목록 날짜가 내림차순이지만 메뉴 15·12에는 날짜 역전이 있다.
  보고서는 최신등록순인데 목록에 발행일만 제공한다. 등록일을 발행일로 대체하거나 가변 목록
  번호를 영속 ID로 간주하지 않는다. 네 메뉴 전체를 두 메뉴의 관측으로 인증하지 않는다.
- 공용 gate를 통한 새 요청 3회로 AMOLF 첫 페이지와 KRIVET 메뉴 12 첫 페이지/15의 13페이지를
  재확인했다. 사이트 차단을 우회하거나 원문 전체를 다시 요청하지 않았다.
- delivery/incremental_holds.json은 원본 수집기 코드 및 원문 검토 파일의 SHA256을 보존한다.
  원본 코드가 바뀌면 보류 근거의 유효성을 다시 확인한다. 새 어댑터가 연결되면 그 경로가 우선한다.
- 새 격리 PostgreSQL에서 기본 worker의 재실행을 측정했다. KRIVET의 네 메뉴 합성 fixture는
  최초/재실행 모두 목록 4회+상세 8회, 저장 8건/0건이었다. 중복 0건이 증분 요청 감소를 뜻하지 않는다.
  AMOLF는 현재 HTML 재생 시 최초/재실행 모두 목록 1회, 저장 0건이었다. 파서 문제를 완료로 기록하지 않는다.
  두 사이트 모두 baseline_complete=false 및 full_rescan_required가 유지됐다.
- 검토 재현: python -m delivery.scripts.review_incremental_order_holds --source <보존된 continuous 경로> --out <새 경로>
  격리 worker 측정은 tests.test_incremental_order_holds_worker이며 기존 DB/테이블을 삭제하지 않는다.

남은 작업과 기준
모든 등록 수집기의 queue 상태를 확인해 pending이 없어야 종료할 수 있다.
접근 차단/인증 필요/정렬 불명/안정적 식별 불가/범위 불명은 각각 증거를 남기고 다른 항목을 계속한다.
단위테스트 성공이나 HTTP 200만으로 수집기 전체 또는 전체 소스 완주를 선언하지 않는다.
