## Background: why each defect exists

Read this before starting. It explains what you are looking at.

**P0-1 — invisible charts.** `src/app/globals.css:32-35` reference `var(--line)` and `var(--accent)`. Neither is defined in `:root` (line 1). When a `var()` reference cannot be resolved and has no fallback, the whole declaration becomes invalid at computed-value time and the property falls back to its initial value — `transparent` for `background`, `none` for `border`. Worse, these three lines *override* working rules: `.taxonomy-bars i` and `.taxonomy-bars b` at line 10 set the correct colors, but `.measure-row i` / `.measure-row b` at lines 33-34 have identical specificity (0,1,1) and come later, so they win and blank the bars out. Result: the "국가별 문서" bar chart on the home page (`src/app/page.tsx:104`) renders numbers with invisible bars, and the "자료 유형별 문서" tiles (`src/app/page.tsx:108`) render with no border.

**P0-2 — unloaded fonts.** There is no `next/font`, no `@font-face`, and no `<link>` anywhere in `src/`. The design's entire typographic identity — the 4.6rem hero, every heading, every stat number — is set in `Noto Serif KR` via `--serif` (`globals.css:1`). Windows does not ship that font, and the next two fallbacks (`Iowan Old Style`, `AppleMyungjo`) are macOS-only, so a Windows viewer falls through to generic `serif` (바탕/Batang). Additionally `font-weight: 650` is used at `globals.css:8` (`.site-name`, `.success-note`); that only renders as 650 with a variable font, which is exactly what the fix loads.

**P0-3 — dead navigation.** `src/app/layout.tsx:30` hardcodes `nav-link-active` on the first link. Every page in the console shows "크롤러 상태" as the current page. `layout.tsx` is a Server Component and cannot call `usePathname()`, so the nav must move into a Client Component.

- Produces: `src/app/fonts.ts` exports `sansKR` and `serifKR` (the objects returned by `next/font/google`, each with a `.variable` className). CSS variables `--font-sans` and `--font-serif` become available on `<html>`; `globals.css` exposes them as the `--sans` and `--serif` design tokens.

**How this works (verified against `node_modules/next/dist/compiled/@next/font/dist/google/loader.js`):** `next/font/google` fetches the family stylesheet at build time and downloads **every** `@font-face` file it references into `.next/static/media`. The `subsets` option only controls which files get a `<link rel="preload">` — it does *not* filter what gets downloaded. Noto Sans KR and Noto Serif KR are each served as 124 unicode-range slices covering Korean, so declaring `subsets: ["latin"]` still self-hosts full Korean coverage while preloading only the small Latin slices. Nothing is requested from Google at runtime.

**Expected costs, so they don't surprise you:**
- First `next build` after this change downloads ~248 woff2 files (~12 MB) and will take noticeably longer than the current ~4s. Subsequent builds use Next's font cache.
- The runtime Docker image grows by roughly the same ~12 MB via the copied `.next` directory.
- A browser loading a Korean page fetches only the handful of slices it needs (~150-300 KB), not the whole family.
- `next/font/google` requires network access during `next build`. `Dockerfile.fe` already needs the network for `npm ci` in the same pipeline, so this introduces no new requirement — but if you build on an air-gapped machine, this task will fail. See the contingency note at the end of this task.

Both families expose a variable weight axis (`font-weight: 200 900` for the serif, `100 900` for the sans), which is what makes the existing `font-weight: 650` declarations at `globals.css:8` render as an actual 650 rather than snapping to 700.
